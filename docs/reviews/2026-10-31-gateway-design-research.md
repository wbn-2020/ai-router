# AI Router：网关设计、渠道配置与模型测试独立调研

- 日期：2026-10-31
- 范围：当前工作区实现、四个本地参考项目、可访问的官方资料、当前管理端实际页面。
- 当前仓库基线：`86bc0ddbf64d2742cc7c060e4d550e860f053734`，**另有未提交改动**；结论针对当前文件，不把旧报告、旧计划或历史测试结果当作本轮验收。
- 本轮性质：调研与设计建议，不是实现计划，也不是授权改造。本轮没有修改业务代码、恢复删除文件、提交 Git、重启服务或调用真实上游模型。

## 1. 核心结论

**不建议推倒 Go＋React＋SQLite 底座，也不建议直接 fork 整个参考项目。需要重新设计的是“配置闭环、模型能力证据、测试语义和运行状态”，不只是换一套样式。**

当前已经实现“创建渠道时选择模型并自动建路由”，但仍存在四个根本问题：

1. **用户的操作单位是“一个渠道及其模型”，界面和 API 却把连接、模型、调试拆成不同保存方式与入口。**新增是三步向导，编辑是分区，模型修改立即生效，基础修改需要保存；取消、同步、测试的语义不统一。
2. **“模型出现于列表”“能生成回答”“支持流式/工具”“任务质量好”是四件不同的事。**当前探针只以 2xx 为主要成功条件，管理端却概括为渠道“正常”。
3. **持久化的最近测试结果不等于当前生产可用性。**生产熔断是另一套内存状态；模型级失败也可能被扩大为整个渠道的隔离。
4. **客户端能力声明缺少逐模型证据。**Codex manifest 的图片、reasoning summary 和统一上下文窗口声明没有与模型能力档案绑定；当前工作区也缺少真实客户端端到端测试。

推荐的产品主线：

> **一个渠道工作台：连接信息 → 同页选择/手填模型与别名 → 逐模型检查 → 看具体结果 → 保存/启用。**

这是一条同页任务路径，不是再增加四步或五步向导。高级路由、网络参数和质量小测渐进展开。

“智商测试”建议产品名为 **模型质量小测**，保留用户容易理解的括注，但不宣传为模型真伪鉴定、通用 IQ 或严格能力认证。

## 3. 四个参考项目：真正值得借鉴的是什么

### 3.1 对比概览

| 维度 | sub2api | new-api | juhe-ai | claude-code-hub |
|---|---|---|---|---|
| 实际上游单位 | Account；Channel 主要是分组/价格/限制层 | Channel 含地址、Key、模型、分组 | Account；连接/厂商/协议面另有层次 | Provider 含 Key/URL/协议，Vendor 聚合，Endpoint 池无 Key |
| 创建时配置模型 | 同弹窗白名单/映射，可手填 | 连接与模型同页，可搜索/自定义/批量粘贴 | 创建向导内多选，但未知模型通常先去模型广场 | 路由区设置白名单/映射，不在最短新增路径 |
| 未保存凭据发现模型 | 有 | 新增有，编辑路径有差异 | 有，但结果与本地目录取交集 | 有，上游失败回退本地目录 |
| 逐模型/批量测试 | 列表独立测试，另有能力探针 | 测试弹窗可逐项/选中/全量 | 连通测试独立弹窗 | 测试区指定模型与预设 |
| 流式/工具验证 | 有部分终态校验；另有强制工具探测但非完整往返 | 流式有效事件检查，不能当作完整协议认证 | 质量套件覆盖 JSON、工具、流式等 | JSON/SSE/NDJSON 解析＋ping/pong，工具闭环不足 |
| 质量/“智商”相关 | 随机小算术内容检查，非题库评测 | 已查范围未见独立质量题库执行器 | 确有 Quick/Full 质量套件，但非标准 IQ，部分自评 | 已查范围未见独立质量题库执行器 |
| 不宜照搬 | 账号/组/定价渠道层、OAuth 和商业治理 | 多 Key 状态、复杂价格、覆盖规则 | 模型广场前置、多进程/PG/Redis 和质量处罚体系 | 域名聚合、端点池、多层熔断、复杂运营预算 |

“不见”仅表示各调研覆盖的测试、监控、模型管理及定向关键词范围未发现，不是对每一条未读代码的绝对不存在声明。

### 3.2 sub2api

**可取点**

- API Key 账号创建在一个弹窗内配置连接和模型；模型选择支持尚未保存凭据发现、手填、追加去重，不轻易抹掉既有选择。
- 静态 ProviderProfile 补默认地址和协议策略，避免每次填所有细节。
- 能力元数据保存 `source/synced_at`，能区分“上游声明”与后来获取的信息。
- 保存后异步探测 Responses 工具支持，方向比单纯 `/models` 发现更接近客户端真实需求。

**边界/反例**

- 同名 Channel 与本项目含义不同，不能直接搬它的数据层。
- 强制工具探测只看是否存在 `function_call`，未核对名称/参数/结果回传，并将一次单模型结果存成账号级布尔值；401/5xx 等还保守视为支持。**这个 true 不等于实测通过。**
- 简单“质量检查”随机生成 1–50 加减题，只要回答中出现任意一个等于正确答案的整数就通过，错误文字夹带正确数字也可能通过。
- 连通测试仍在独立弹窗，不是完美同页配置闭环；部分流解析器将普通 EOF 当成功。

### 3.3 new-api

**可取点**

- “连接与模型”同页；搜索多选、未知模型输入、逗号/换行批量粘贴更适合中转站用户。
- 获取上游模型后区分新增、已有与未返回；未返回不立即删除。
- 测试复用实际适配器的映射、参数与响应处理；弹窗支持逐模型、选中、全部，展示进度和失败项。

**边界/反例**

- `/models` 发现主要提供 ID，静态“填充相关模型”不是可用性证明。
- 测试模板主要是 `hi`，流式检查非空 `data:` 不等于严格终止、正确语义和工具往返。
- 后台“全部渠道测试”每渠道一个代表模型，不是全模型覆盖。
- 价格解析位于测试之前，未配置价格可能阻止连通性验证。个人网关不应把价格完整性变成接入门槛。
- `Ability` 表是组×模型×渠道路由关系，不是模型智力/能力评分。

### 3.4 juhe-ai

**可取点**

- 厂商预设、创建中配置模型、编辑高级项折叠、未保存 API Key 的草稿连通测试。
- 文本探针不仅检查状态码，还检查协议完成证据和随机算术回答。
- **确实存在 Quick/Full 质量检测**：基础文本/流式、结构化输出、工具参数、usage，进一步增加行为题、长上下文、稳定性、Token 差分和可选对照。

**边界/反例**

- 模型发现结果是各 Key 上游列表交集再与本地厂商目录取交集；未知上游模型不能直接在渠道表单创建。这会重现“先去模型页再回来”的繁琐路径。
- 三步向导后两步可跳过、每步可创建，并不天然保证接入完成。
- 多 Key 任一探针成功即停止，不能扩大为全池可用。
- 身份自报、Token 差分和行为相似性只是弱线索，不能证明真实模型身份。
- 题库回答与判分都使用被测模型，只是换了隔离上下文；缺少独立裁判。固定扣分池不是经过科学校准的 IQ 标尺。
- 质量检测可能影响调度/质量隔离，不是纯观察。个人版不应默认照搬一次小测触发处罚的机制。

### 3.5 claude-code-hub

**可取点**

- 最短新增只填少量连接字段；已有 Vendor/Endpoint 时可以继承，减少重复。
- 模型候选优先从上游取得，失败回退目录并标注来源。
- 测试展示 HTTP、解析输出、usage、流块数和原始结果；实际代理关注流式提交边界和故障决策链。

**边界/反例**

- Vendor 按域名聚合并不证明多个端点都接受/可信地持有相同 Key。端点和凭据复用必须显式授权，不能靠官网相同推断。
- 默认端点探活是 TCP；HTTP 探活 `status < 500` 即成功，401/404/429 都能表示“可达”。不能把它画成模型健康。
- API 测试主要基于 ping/pong；完整缓冲后解析，`firstByteMs` 在响应头返回时测量，并不等于首 token 时间。
- 模型规则、网络、预算、熔断等长表单不会因为分成六个滚动区就变简单。

## 4. 官方资料补充：可借的设计原则与获取限制

### 4.1 已取得正文的资料

1. **Cloudflare AI Gateway 动态路由**：路由别名与具体模型节点解耦；可配置规则、限额并保存/部署版本。当前页面明确的协议边界是 OpenAI Chat 结构，不能推成任意协议自动互转。对个人网关借鉴“稳定别名＋明确规则”，不照搬流程图编辑器。
2. **Cloudflare 日志**：整条日志开关与 payload 保存开关不同；可以保留元数据而不保存原始正文。对本项目有价值的是故障可观测与 prompt 隐私分离，不要求默认保存全部 body。
3. **Anthropic 官方工具评测 notebook 原文**：题目和标准答案、工具 schema、逐项答案/耗时/调用数、客观相等判分。说明工具评测可以成为小型可重复任务集；示例中的动态求值不是可直接搬进生产的安全执行方式。
4. **OpenAI Cookbook 评测迁移文章原文**：提示词、模型配置、样本、断言和指标应配置化；判分方式迁移后必须校验，尤其 LLM grader，不能默认与旧评分等价；可以在本地/CI 持续运行。
5. **LiteLLM 官方首页**：统一提供方调用、密钥/预算/调用观测是其定位。首页材料不足以确认具体 Router cooldown 和健康检查机制，本报告不据此作详细机制对比。

本项目的取舍判断：**基础兼容检查做在网关内，深度评测可以通过本地题集或独立评测工具连接网关运行。**这是设计建议，不冒充上述文章的原话。默认不把业务请求自动复制到外部评测服务。

### 4.2 获取限制

- 本会话 WebSearch 返回不支持的 provider API 错误，不能称为完成全网最新搜索。
- OpenAI 平台评测最佳实践/新 Cookbook 页面返回 403；Anthropic 平台文档发生区域不可用重定向；LiteLLM 路由页多次超时。
- GitHub CLI 不在当前 PATH；部分 GitHub 页面只返回目录或导航，只有取得正文的资料用于实质结论。

因此本报告是 **四个本地快照＋有限官方资料的可核实研究**，不是 2026 年全部商业网关的穷尽排行榜。

## 5. 当前设计审查：优先缺口

优先级含义：P1 为先于扩大功能修正的可靠性/契约问题；P2 为下一阶段治理与体验问题。不是安全漏洞评级。

### D01 · P1 · 探针将 2xx 误概括为有效推理与渠道健康【确认】

实际发送了非流式 `ping`，随后把前 64KiB 丢弃。没有验证 JSON/协议结构、error 字段、非空模型输出和完成状态；HTML、`{"ok":true}` 或提前到读取上限都可能通过。已有单测明确使用 `{"ok":true}` 判 healthy。延迟测量截止响应头，不是完整推理耗时或 TTFT。

**影响**：错误端点、伪兼容上游、仅回 reasoning 或截断输出可被显示成“正常”；用户真正调用仍失败。

**建议**：分离连接、模型推理与能力结果；最小推理检查正确结构、错误字段、完成状态、有效内容；预算不足/取消/限流标不确定或对应故障，不能直接标能力不支持。

证据：`internal/upstream/probe.go:14`、`internal/upstream/probe.go:118`、`internal/upstream/client_test.go:801`。

### D02 · P1 · 模型发现与客户端能力声明没有证据闭环【确认】

发现只提取 `data[].id`。Codex manifest 对任意映射统一声明图片输入、reasoning summary 支持和统一上下文窗口，未按模型区分；注释称“保守”并不能让实际字段成为已验证能力。

**影响**：客户端可能发送某个上游不支持的图片、参数或过长上下文，故障被误归为请求问题。

**建议**：少量能力元数据即可：支持入口、流式、工具、图片、结构化输出、上下文/输出限额。分别记录声明来源、人工覆盖、实测状态；unknown 不冒充 true。manifest 的安全默认和人工覆盖应来自此证据，不依赖模型名字猜测。

证据：`internal/upstream/models.go:106`、`internal/gateway/codex_models.go:162`、`internal/gateway/codex_models.go:203`、`internal/gateway/codex_models.go:221`。

### D03 · P1 · 最近手工测试与当前生产状态是两套状态【确认】

测试写 `channels.last_health_*`；生产调度只看内存熔断，生产成功/失败不会同样刷新这组字段。测试没有记录模型、协议、配置代次与来源；模型测试将 Chat/Responses 候选合并后只测试第一条，并绕过生产并发/熔断。

**影响**：页面“正常”与生产被熔断可同时存在；Chat 测通被误解为 Codex Responses 可用。

**建议**：列表分开呈现“启用状态 / 当前运行状态 / 最近测试”。直接上游检查固定渠道模型协议；客户端路径检查使用真实生产调度，两者明确标注，不能互相冒充。

证据：`internal/adminapi/debug.go:50`、`internal/adminapi/debug.go:144`、`internal/adminapi/debug.go:231`、`internal/routing/scheduler.go:199`。

### D04 · P1 · 故障分类没有足够的影响范围【确认】

401/403、429、5xx 按整个渠道打开熔断；SSE 错误统一记录为状态 0。模型权限/限流可能损害同渠道其他模型。400 一律不切换，404 可切换但不会形成模型级隔离；局部凭据解密失败也可能阻止备用渠道。

**建议**：先建立小型稳定分类，再决定 retry/scope/cooldown，而非所有错误读状态码：客户端输入、模型/能力、渠道鉴权、容量/限流、网络/协议。不识别的错误不冒充精确范围；按 `Retry-After` 和配置给出有界冷却。

证据：`internal/gateway/attempt.go:75`、`internal/gateway/stream.go:868`、`internal/routing/scheduler.go:515`。

### D05 · P1 · 熔断恢复有并发交错问题【机制确认，发生频率未验证】

窗口到期直接全面放行；任何旧请求成功都删除渠道状态；后来失败直接覆盖新窗口，较短窗口可能替换较长鉴权窗口。配置更新没有代次约束，旧结果可影响新凭据状态。

**建议**：简单 generation/revision、同范围截止时间合并、单个半开恢复许可即可；不能让一次弱探活重置所有模型或凭据故障。无需引入复杂评分调度器。

证据：`internal/routing/scheduler.go:466`、`internal/routing/scheduler.go:486`、`internal/routing/scheduler.go:496`。

### D06 · P1 · 当前工作区缺少真实客户端端到端保障【确认】

`e2e/` 当前为空，原 Codex/harness/fake_upstream/template 四个 tracked 文件被删除，共 1808 行。`cmd/gateway/dataplane_test.go` 仅测试鉴权、模型列表与入口挂载，没有启动真实 Codex、工具、图片或流式任务。

**影响**：原需求中的 Codex/ZCode 核心客户端契约不能以当前自动验收证明。不能因为某次历史测试通过就对当前版本作承诺。

**建议**：后续建立最小固定版本客户端契约集；ZCode 协议与版本要基于实际配置确认。删除原因未确认，本轮不恢复或覆盖这些文件。

证据：当前 `e2e/` 目录及 Git 工作树；`cmd/gateway/dataplane_test.go:19`；`docs/requirements/api-gateway.md:20`。

### D07 · P1 · 没有端到端请求预算与完整资源边界【确认】

每次上游尝试重新设置单次超时；多渠道重试＋容量等待会累加。HTTP Server 只有读头/空闲等限制，没有读体和下游写出截止；慢客户端写流时可能长时间占有渠道槽。并发上限也不是需求中的速率限制。

**建议**：先补端到端预算、首有效输出/读空闲/下游写截止、有界等待人数；RPM/TPM 再按实际需要加进程内小型限额。流式不能简单使用固定全程 WriteTimeout，需可续期写出 deadline。

证据：`internal/upstream/client.go:293`、`internal/server/server.go:183`、`internal/gateway/stream.go:202`、`docs/requirements/api-gateway.md:47`。

### D08 · P2 · 编辑、同步与取消不满足一个配置事务【确认】

新建渠道＋初始映射同事务是优点。但编辑基础是草稿；模型添加/删除/启停即时提交；批量导入逐项请求，失败留下部分成功，后续又清空选择。同步用已保存 Key/URL，不是正在编辑的新值。旧健康结果不因连接变化失效。

**建议**：渠道编辑只采用一种语义：连接和模型都在草稿，显式保存一并提交；即时启停只能在列表明确作为独立动作。同步是“获取候选”，对比新增/已有/未返回后由用户确认；失败保留失败项。配置变化让旧测试标过期，而非继续绿灯。

证据：`web/src/features/channels/ChannelEditor.tsx:208`、`web/src/features/channels/ChannelModelsTab.tsx:89`、`web/src/features/channels/ChannelModelsTab.tsx:129`、`internal/store/channels.go:379`。

### D09 · P2 · 配置候选快照与运行生效时机不清【确认】

容量等待复用候选快照；等待中停用渠道或降低并发后，仍可能按旧配置取得槽位。PATCH 是读后合并，没有冲突版本。

**建议**：轻量配置 revision；取得槽位后再确认关键可用性。单管理员也存在多个页签和后台任务，不能把“单用户”当作无并发更新。

证据：`internal/routing/scheduler.go:300`、`internal/store/channels.go:379`。

### D10 · P2 · 上游出站目标与脱敏策略需按部署区分【确认，风险依部署】

草稿发现已鉴权、同源、有限超时和 body 大小，也不会偷偷借用已存 Key，这是有效防护。但目标只校验 URL 格式，未限制解析后的私网/回环/链路本地目标。URL 查询串可持久化/展示，不能藏 Key；正则脱敏不是任意秘密的保证。

**建议**：个人本地上游合法，不能简单禁止私网；提供明确网络目标策略。公网部署限制未授权目标，拒绝 URL userinfo/秘密查询参数；凭据只进认证头；不要记录草稿 Key 和原始上游错误体。测试响应正文按长度限额、以纯文本安全显示。

证据：`internal/adminapi/model_discovery.go:36`、`internal/upstream/client.go:148`、`internal/upstream/client.go:428`、`internal/secret/redact.go:46`。

### D11 · P2 · 观测只看最终请求，容易掩盖故障渠道【确认】

切换成功后，之前渠道的失败保存在 attempts，却不体现于渠道最终请求统计；用户取消与上游错误也混在错误率中。部分前置拒绝记录空 protocol，仓储拒绝后写入错误被忽略。

**建议**：至少加 attempt 级失败统计、错误范围、取消分组、日志写入失败计数。诊断结果带 test/run/request ID，日志入口携带精确模型/协议/渠道筛选，而不是跨页重新选择。

证据：`internal/gateway/observability.go:304`、`internal/observability/record.go:441`、`internal/observability/query.go:244`。

### D12 · P2 · 恢复前逻辑兼容校验仍不完整【确认】

已有一致性备份、恢复前备份与副本 integrity 检查。预检查未复用迁移 checksum、外键和完整列约束检查；可能先覆盖，重启才报不兼容。停服恢复主要依操作约定，checkpoint 不等于生命周期独占锁。捕获数据 TTL 不会自动清理历史备份里的密文。

**建议**：替换前复用只读逻辑校验，最小独占保护，独立备份保留/删除策略。本轮不做恢复试验。

证据：`internal/store/backup.go:149`、`internal/store/backup.go:231`、`internal/store/migrate.go:129`。

### 尚需实证的协议问题

- `previous_response_id` 等上游会话状态能否跨渠道使用；保留字段不等于支持无状态切换。
- 首有效输出前重试也可能已在上游完成计算/计费，不能承诺没有重复成本。

建议将有上游状态依赖的请求绑定原目标，或明确禁止跨渠道重试；这是待确认契约，不要先做复杂亲和系统。

## 7. 推荐产品设计：一个渠道工作台

### 7.1 信息架构

- **渠道**：主要工作入口；列表与详情工作台。
- **模型**：全局聚合视角，回答“客户端模型由哪些渠道/入口承载”；别名和优先级在这里处理，不要求普通新增先来此页。
- **请求**：生产观测、错误与 attempts。
- **接入**：Codex/ZCode/普通客户端配置与入口说明。
- **管理员安全**：密码和 sessions。可收在设置中，不伪装成渠道配置中心。

诊断是渠道/模型详情的一部分；深度测试历史可以独立查看，但正常接入不强迫进入独立“调试”页。

### 7.2 同页默认布局

```text
渠道 / 新建                         草稿 · 尚未启用

连接
[接入预设]      [客户端用途/明确协议]
[Base URL_________________________]
[API Key__________________________]  已存凭据留空不变
[名称（自动生成，可改）____________]
请求路径预览                       高级设置 ▸

模型                              获取候选   手动/批量添加
搜索模型                           当前筛选选择范围
使用  上游模型           客户端名   入口     最近检查     操作
☑     model-a           model-a   Responses 未测        检查
☑     upstream-model-b  alias-b   Chat      未测        检查

检查所选：基础推理 / 流式 / 工具       质量小测（可选） ▸
逐项结果：成功/失败/不确定/跳过、时间、原因、日志入口

保存草稿         保存并检查          启用（显式决定）
```

- 名称可以自动生成，普通用户主要填地址、Key 和选模型。
- 协议不能真正消失：用客户端用途提供默认，让用户看见“将调用 `/responses` 或 `/chat/completions`”。不推测上游支持，也不偷偷转换协议。
- 模型公开名默认与 wire ID 相同；别名按需编辑。未知模型允许直接手输，模型目录只是建议。
- 高级项首期只放优先级、并发、超时/网络策略等确有实现的参数。不要为了参考项目功能多而塞倍率、组、账单。
- 质量小测不在必填流程，不默认启动全部模型的长题集。

### 7.3 保存与测试生命周期：推荐明确的一种默认语义

1. **表单改动均为草稿**。模型增删/映射/连接不再混合即时提交。
2. **保存草稿**：一次本地事务提交渠道和模型，首次不参与生产调度。
3. **保存并检查**：先原子保存当前配置，再对所选模型发起有限检查，结果就在当前页面。数据库事务内不等待网络。
4. **启用**：明确动作。可以只启用已选项；跳过检查允许存在，但显示“未验证”，不声称健康。
5. **测试失败不撤销已保存配置**，保留结果、失败项与修复入口；失败也不自动禁用其他已经正常使用的模型。
6. 编辑有未保存改动时，要么明确“保存后检查当前改动”，要么显式草稿检查；**禁止静默使用旧 Key/URL 测新表单**。

后续可增加无需落库的草稿推理检查，和现有 preview-models 共用校验/目标策略。没有必要引入持久服务端草稿系统。草稿结果不能靠客户端传 `passed=true` 成为健康证据；只有服务端实际产生且绑定配置的结果可以持久化。

### 7.4 模型同步语义

按钮应称“获取候选”或“比较上游模型”，而不是暗示自动完成同步。

- 显示来源和时间：上游发现 / 本地建议 / 手填。
- diff：新增、已有、上游此次未返回。未返回≠失效，不自动删除。
- 保留别名和手填项；选择当前筛选结果，不默认所有候选全发布。
- 批量提交选择：推荐事务原子提交；若选择逐项 API，则必须逐项展示部分成功/失败，保留失败选择。

## 8. 连通性、兼容性与“智商测试”的合理设计

### 8.1 四层检查，加一层客户端验收

| 层次 | 目的/输入 | 成功证据 | 不能证明 |
|---|---|---|---|
| 连接与鉴权 | 目标、Key；尝试模型列表或明确检查端点 | TLS/HTTP 可达、鉴权被接受；保留具体结果 | 没有 /models 不等于无法推理；可达不等于模型可用 |
| 指定模型基础推理 | 固定渠道＋wire ID＋明确协议 | 合法响应结构、无错误、终态、非空有效内容；小任务可核对结果 | 所有模型、所有参数、工具/图片都正常 |
| 协议/能力检查 | 流式、工具往返、JSON、图片等选定项 | SSE 终态/参数拼接；受控工具名/参数/结果往返；schema/小图客观断言 | 通用质量和真实模型身份 |
| 模型质量小测 | 版本化任务集与参数 | 逐题客观断言、重复记录、覆盖/排除范围 | IQ、科学排名、无法被代理欺骗的身份认证 |
| 实际客户端契约验收 | 固定版本 Codex/ZCode＋真实生产入口 | 文本、多轮、工具、图片、取消、流式/故障边界实际通过 | 任意未来客户端版本、任意上游协议都兼容 |

### 8.2 第一版检查套件

**快速检查**：用户选定模型后默认基础推理；流式作为核心客户端必需项。工具检查按明确用途选中，不对所有模型盲测。

- 基础：返回指定短随机标记，验证协议结果和完成状态。失败要区分“指令未遵循”和“响应无效”。
- 流式：检查 Content-Type、有效内容增量、错误事件与正确终态；工具参数增量也要可拼接。响应头时延、TTFT、完整耗时分开。
- 工具：强制一个受控、无副作用的本地工具，验证名称与 JSON 参数，返回固定结果，再要求模型给出最终答案。不能只检测一个 `function_call` 字段。
- 结构化：客观校验小 JSON schema。格式未支持与推理失败分开。
- 图片：仅在用户选了图片用途时用本地合成的小图做客观识别；不上传私人截图。
- reasoning/context：默认记录声明；预算截断不判断为能力不支持。完整窗口极限不是免费快速检查，不默认测。

工具执行必须限于白名单纯函数；不跑任意 shell、Python 或文件操作。

### 8.3 模型质量小测

建议首版 **8–12 个可客观判分的小任务**，偏向用户的代码/工具使用场景，而不是照搬一个庞大排行榜：

- 数字/约束推理：生成新参数，严格解析答案，不做“文本包含正确数字”判定。
- 指令约束与结构化提取：校验字段、顺序或限制。
- 工具选择/参数/往返：无副作用工具的确定结果。
- 小代码阅读/修复题：先用预定义检查和人工 rubric；需要执行代码的评测留给真正隔离的独立工具，不在网关服务进程执行。
- 小规模长上下文检索：长度和覆盖范围明确，不称为全窗口验证。

设计要求：

- 固定 suite/version/seed/参数；保存按题明细，不只一个百分制总分。
- 默认一次轻测；怀疑波动时显式重复，显示重复次数和离散情况。温度 0 也不保证完全确定。
- 客观断言优先；主观题采用独立、显式配置的 grader 或人工判分。不能默认被测模型给自己评分。
- 限制模型数、题数、输入/输出预算、总时间与并发；启动前显示请求上限与费用未知/估计来源。
- usage 和成本可能由上游自报；缺失时显示未知，不杜撰精确金额。
- 基础鉴权/模型不可用时停止深测，显示因前提失败而跳过，避免继续消耗。
- 失败不自动改变生产路由、启停或熔断。后续自动策略必须独立评估误判成本。

**不提供“模型真伪已鉴定”绿灯。**响应 model、身份自报、Token 特征、回答风格都可能被代理修改；可信对照能发现偏差，仍不是加密身份认证。真正真实性依赖供应商可信度、可验证访问路径/凭据和合同审计，而不是几道题。

### 8.4 测试状态模型

每个检查项至少支持：`未测 / 运行中 / 通过 / 失败 / 不确定 / 不适用或跳过 / 已过期`。

- 通过：该版本用例在该配置上通过。
- 失败：明确失败证据；区分网络/鉴权/协议/答案。
- 不确定：限流、预算截断、暂时服务故障等，不能推为能力 false。
- 跳过：未选能力、前置失败或不适用；不计入通过。
- 过期：连接/Key/协议/模型/测试版本改变，旧证据仅作为历史。

展示成功数必须说明分母：例如“已测 2/5 个模型”，不能写“渠道正常”。

## 9. 数据与架构：补足证据，不复制商业平台层次

### 9.1 推荐最小逻辑模型

| 概念 | 职责 | 对用户的呈现 |
|---|---|---|
| Channel | 一组明确可信的上游连接与凭据、网络策略、配置 revision | 一个渠道工作台 |
| Model binding / route | 上游 wire ID、客户端别名、入口/协议、启用和优先级 | 渠道内模型行；全局模型页为聚合视角 |
| Capability metadata | 声明值、人工覆盖、实测状态与来源/时间 | 可选能力详情，不是必填目录 |
| Test run / result | 配置代次、suite/version、模型/协议、逐项状态、时间/用量 | 模型行最近检查与历史 |
| Runtime health | 故障范围、冷却/恢复状态、槽位与近期 attempts | 当前运行状态，与测试分列 |

现有 `channels + model_routes` **足以表达简单路由，但不足以表达能力与测试证据**。不能再用“不加表”作为设计质量目标。

可以先扩展现有映射与轻量测试记录；是否把多个别名复用的上游能力抽成独立 binding，需要结合实现计划决定，避免重复状态漂移。暂不需要全量价格目录、Vendor/Account/Group 三层体系。

### 9.2 单协议渠道需要重新定边界

当前 `channel.protocol` 是一个固定入口。真实中转站同 URL＋Key 经常同时提供 Chat/Responses：如果简单复制成两个渠道，会拆开凭据、并发、故障与测试管理。

**推荐产品概念**：一个连接/Key 是一个渠道，协议能力属于该渠道的模型绑定或端点配置；UI 不要求用户重复输入 Key。

**实现约束**：不把 `auto` 等同于隐式转换或错误后盲猜路径；明确选择/检测受支持入口。第一阶段可以保留现有单协议存储并清楚标注，等多入口需求有实证后做小型扩展，不能直接宣称它已经满足双协议共享配额。

### 9.3 服务边界

- 配置服务：校验、加密、原子写入、revision；不等待上游网络。
- 模型发现：只读取候选，限额、来源和手填 fallback。
- 诊断服务：复用生产 transport/auth/URL 拼接/协议解析，固定检查目标；额外短超时和检查预算。
- 生产路径检查：使用生产路由/并发/错误分类，明确可能调用备选。
- 质量服务：低优先级、有界本机 Go worker；不放在业务请求热路径，不引入 Redis/MQ。
- 观测：生产与 test 来源可区分；不将测试用量混入普通成功率。

首次无需通用插件系统、模型评分路由、概率图或跨协议转换引擎。

### 9.4 最小安全要求

- 已保存 Key 在服务端按 ID 解密用于检查，不为测试回传浏览器。
- 编辑留空 Key＝保持；明确替换才更新，取消不覆盖。
- 草稿出站只带明确提交的凭据，出站目标受部署策略保护。
- 结果只展示限额、脱敏、转义的正文；不能将模型输出当 HTML 或指令执行。
- 质量任务不读取生产 prompt，不自动发送第三方 grader；外部判分要明确目的和成本。
- 窗口关闭/取消中止检查；重启后的 running 标中断，不能无提示续跑付费题集。
- 数据库保存配置与密钥密文，浏览器 widget/本地持久状态不保存 Key。

## 10. 推荐改造顺序与验收门槛（不是待执行计划）

### 阶段 A：先把“可用”定义正确

- 修正探针有效响应/完成状态；分离测试与运行状态。
- 核对实际客户端契约、能力声明和有状态请求重试边界。
- 修正模型/渠道故障范围与恢复代次；加端到端请求预算。

验收反例：HTML 200、空 JSON、HTTP 200 error、只 reasoning、缺终态 SSE、权限只影响一个模型、旧请求成功不能清除新鉴权故障。固定客户端要跑到工具/图片/流式任务，不只 GET models。

### 阶段 B：渠道工作台与整体配置

- 同页连接＋模型；全局模型视角聚合。
- 整体保存/取消，候选 diff、未知模型手填，来源与过期状态。
- 逐模型快速/批量检查、结果行直达详情；高级项折叠。
- 统一 token，移走危险/低频操作，修复焦点、移动布局和保存定位。

验收：从空库创建一个可用模型不离开当前页面、不预先创建目录模型；改 URL/Key 不测旧配置；取消不留下模型改动；批量失败可重试失败项；搜索全选不超范围；320/768/1280px 无重要信息裁切。

### 阶段 C：可选能力与质量小测

- 先工具往返/JSON/图片，再有限质量任务；不引入自动质量处罚。
- 版本化题集、客观断言、明细/历史、预算与取消。

验收：跳过不计成功；预算不足不计能力不支持；费用未知可见；结果绑定配置；无任意代码执行；被测模型不能默认自评分；没有“真伪认证”结论。

### 阶段 D：确有需求时的扩展

- 同连接多协议模型绑定、共享配额、多 Key/端点池。
- 限额、备份逻辑校验、长期观测和外部评测接入。

只有真实使用数据证明有必要才增加，不复制完整运营网关。

## 11. 取舍清单

**保留**：原生协议直通、Go/React/SQLite、加密 Key、统一客户端入口、初始渠道/映射事务、流式提交后不透明换上游、元数据优先日志、显式 body 捕获。

**重做**：渠道配置的信息架构、保存/取消/同步语义、健康展示、探针成功条件、模型能力证据与客户端声明、故障范围/恢复、实际客户端验收。

**新增但克制**：逐模型批量检查、测试历史/revision、工具往返/JSON/图片检查、可选小题集、轻量客户端接入说明。

**本轮不建议**：运营分组/倍率/充值、全量模型广场前置、质量排名自动路由、任意协议转换、多层端点/Key 池、微服务/Redis/MQ、测试期间自动发送生产 prompt 或自动禁用渠道。

最终推荐不是“重新堆更多功能”，而是：

> **让最常用任务一次完成，让每个状态有证据，让不确定性诚实可见。**
