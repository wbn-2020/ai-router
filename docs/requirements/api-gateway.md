# 个人 AI API 网关 v2 需求与设计约束

## 项目状态

这是一个绿地项目：当前工作区只有 docs/ 和 reference/，没有业务源码。

参考仓库位于：

- reference/sub2api
- reference/new-api
- reference/juhe-ai
- reference/claude-code-hub

当前使用 juhe-ai，但作者持续增加与个人使用无关的功能，导致复杂度和不稳定性上升。本项目要做自己的、自托管的 AI API 网关，稳定优先、功能克制、长期可维护。

不要求兼容或迁移 juhe-ai 的现有数据。

## 已确认的产品决策

1. 个人自用，单用户；不做多租户、注册、支付、充值、返利和复杂权限。
2. Codex 和 ZCode 都作为第一版核心客户端，必须实际接入验收。
3. 网关对客户端只使用一个统一 API key。
4. 第一版能力：文本对话、SSE 流式、tool calling、图片输入。
5. 第一版不做：embeddings、图片生成、音频转写/TTS。
6. 管理端：基础管理 + 观测统计 + 调试；参考 sub2api、workbuddy2api-panel 等中转站面板，布局不能过于简陋。
7. 管理端使用单管理员密码 + session；不做多用户权限。
8. 上游 Key 默认脱敏展示；点击后直接显示完整明文，不做二次密码验证。
9. 请求日志默认仅保存元数据、token、延迟和错误；完整请求/响应 body 只在管理员按需抓取时保存。
10. 统计第一版包含请求数、输入/输出 token、延迟、错误率和渠道维度；完整费用账单、对账和实际扣费同步后续再做。
11. 技术栈固定为 Go 后端 + React/TypeScript 管理端；SQLite 单文件存储。
12. 先在本机运行，但架构要能迁移到 Linux + Docker；第一版不引入 Redis、消息队列、微服务。
13. 不从 juhe-ai 迁移，渠道、Key 和模型映射重新配置。

## 客户端与协议

- Codex 和 ZCode 都会使用文本、图片输入、tool calling 和流式输出。
- 两者目前可能通过同一个中转站 API key 接入，但不能假设两者发送的协议完全相同。
- 计划必须先核实 Codex/ZCode 实际使用的入站协议和 endpoint，例如 Chat Completions、Responses API、Anthropic Messages；不能凭猜测实现。
- 如果两者协议不同，优先支持它们实际使用的协议；如果信息不足，列入 blocking questions，不要静默丢弃图片、tool call 或流式字段。
- MVP 至少提供 OpenAI-compatible 入口；Codex/ZCode 需要额外协议时，增加对应适配，不要只做纯文本转发。

## 上游渠道与路由

- 上游主要来自多个中转站，常见由 new-api 或 sub2api 搭建；模型包括 GPT、Claude、Gemini、Grok、DeepSeek、GLM 等。
- 第一版按可配置 channel 管理：base URL、API key、支持模型、优先级、并发上限、启停状态。
- 模型到渠道的映射由管理员手动配置；第一版不做自动模型发现。
- 同一模型可以有多个渠道，按优先级和可用性调度；请求失败时切换到下一个可用渠道。
- 需要渠道级并发/速率限制，避免单个中转站被压垮。
- 客户端“尽量无感”是目标，但必须诚实描述流式限制：
  - 未输出首 token 前，可以切换渠道重试；
  - 已经输出流式内容后，不能默认承诺无缝切换；
  - 对比四个参考项目是否有更好的重试/续传方案；如果没有，默认终止并让 Codex/ZCode 自行重试。
- 渠道并发满载时的行为需要对比参考项目后确定：优先切换其他渠道、短暂排队或返回 429；无论选哪种，都要有明确超时和验收。

## 管理界面

第一版至少包含：

- 渠道管理：新增、编辑、删除、启停、优先级、并发上限、健康状态。
- 上游 Key 管理：脱敏列表、点击显示明文、复制。
- 模型映射：模型名、渠道、优先级、启停。
- 请求观测：请求数、token、延迟、错误率、按模型/渠道筛选。
- 请求日志：默认元数据，支持对单次请求按需抓取完整 body。
- 调试：渠道连通性测试、模型测试、错误详情。
- 管理员登录和 session 管理。

布局参考 sub2api、workbuddy2api-panel 等中转站管理面板，但只保留个人使用需要的功能，不抄多租户、支付和运营模块。

## 安全与稳定性

- 上游 Key 在 SQLite 中加密存储，主密钥从环境变量读取；不能以明文落库。
- 管理端使用单管理员密码；上服务器后由 TLS 反向代理保护。
- 日志默认不记录完整 prompt；按需抓取时必须明确提示风险。
- 配置校验、数据库迁移、备份/恢复、优雅退出、健康检查。
- 上游连接设置超时、重试上限和错误归一化。
- 不自动回滚用户数据；任何数据库迁移都要可恢复。
- 参考项目代码必须检查许可证，不直接复制不兼容代码。

## 必须调研并决策

1. 路线对比：从零实现、fork new-api、fork sub2api、裁剪 juhe-ai，以及 claude-code-hub 的可借鉴设计。比较维护成本、许可证、上游同步、功能覆盖、UI 复用和迁移风险，给出明确推荐。不要默认从零。
2. 四个项目的渠道模型、模型映射、路由调度、失败切换、流式处理和错误格式；哪些值得借鉴，哪些是复杂度反例。
3. Codex/ZCode 的实际入站协议和 endpoint，以及第一版必须提供的兼容入口。
4. Provider Adapter 的边界：统一 OpenAI-compatible，还是保留原生 Anthropic/Gemini 适配；参考 juhe-ai 的聚合做法。
5. 流式响应中断后的重试/切换策略，并明确哪些情况不能做到无感。
6. 渠道并发满载时的调度行为。
7. 管理界面页面和布局，参考 sub2api/workbuddy2api-panel，但不能变成功能堆砌。
8. 稳定性策略：依赖锁定、SQLite 备份、迁移、上游契约测试、故障隔离和升级回滚。

## 计划交付要求

- 使用 strict 模式生成 docs/plans/api-gateway-plan.md。
- 只读调研，只写计划；不执行计划，不修改业务源码。
- 计划必须包含：requirements 覆盖矩阵、目标架构、模块边界、数据模型、API surface、管理界面页面、路由和失败切换、Provider Adapter、鉴权、安全、部署、观测、测试策略、MVP/非目标/路线图。
- 每个 ready 任务必须包含：文件范围、步骤、行为验收、风险缓解、依赖、唯一 argv 验收命令。
- 验收必须是行为验收加真实测试；不要用 git status 或文件存在性检查冒充验收。
- 不要使用 shell；不要使用 python -c 这类拼接脚本；优先使用 Go 测试、构建命令和前端测试命令。
- 如果选择 fork 某个项目，必须说明许可证、后续上游同步方式和裁剪范围；如果技术栈与 Go + React/TS 冲突，必须明确说明，不要静默改栈。
- 证据不足或产品决策未定时，列入 assumptions 或 blocking questions，不要编造。
- 必须先通过独立评审；在我明确批准前不可执行。
